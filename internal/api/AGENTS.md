# API

## Purpose
Exposes HTTP REST routes, authentication endpoints, Single Sign-On callbacks, SCIM endpoints, backup restore drill handlers, and static React PWA hosting.

## Ownership
Owns HTTP routing, request parsing, session cookie validation, CORS headers, and error response formatting.

## Local Contracts
- `GET /api/admin/network-check` (`requireAdmin`, `no-store`) reports how the request arrived: `peer_ip`, `client_ip`, `forwarded_trusted`, `forwarded_proto`, `app_url_https`, `host_matches`, `trusted_proxies_narrow` (true only when every `KY_TRUSTED_PROXIES` prefix is a single address, /32 or /128; false when empty). Admin-only because it describes the deployment's wiring. `forwarded_proto` is reported only when the direct peer is in `KY_TRUSTED_PROXIES`; otherwise forwarded headers are ignored and it is empty.
- POST `/api/auth/change-password` accepts a restricted local session, current password and a different policy-valid new password. Browser CSRF and per-IP/account limits apply. Success revokes all sessions and requires sign-in again; flagged sessions get `password_change_required` on protected routes and public-only settings.
- All JSON API endpoints return structured errors `{"error": "message"}` upon failure.
- `/api/auth/me` returns `Cache-Control: no-store` for both signed-in and anonymous
  responses so browser device setup never uses cached account status.
- Non-API routes fall back to serving `web.Handler()` for client-side SPA routing. Unmatched `/api/` paths answer a JSON 404 (`Unknown API endpoint`), never the SPA's 200, so a webhook sender on a retired or mistyped route retries instead of being falsely acknowledged (`TestUnknownAPIPathIsNotAcknowledged`). A wrong method on an `/api/` route also gets this 404 rather than 405.
- New routes are unauthenticated only by deliberate choice; privileged ones are registered wrapped in `s.requireAdmin` in `routes()`, so the trust level of every route is readable in one place.
- Deposit, export and drill return 413 for oversized snapshots through `writeTooLarge`, which
  names a `*backup.SizeError`'s size and member. Each sets its own write deadline
  (`depositWriteBudget`, `exportWriteBudget`, `drillWriteBudget`, each counting
  `backup.DumpTimeout`): the listener's 15s `WriteTimeout` is for JSON replies. All three
  routes are `tracked`; export audits after the download, with `outcome` `delivered` or
  `interrupted`, on a detached context.
- Backup capsule/status versions use `config.AppVersion`, shared with the CLI.
- Backup status includes the latest recorded `admin.backup_run` as `last_run`:
  outcome, trigger, recorded timestamp and capsule ID only. Classify the known audit
  prefix; legacy formats are unknown and partial destination/receipt failures are
  warnings. Keep raw audit/error details out of this DTO. A failed audit lookup is
  a visible `last_run_error`, not an invented success or empty history. This result
  is separate from the last successful remote receipt.
- Backup handlers seal the server capsule; `last_run` reads the `admin.backup_run` audit action. Status also carries `capsule_size` and, with Matrix, `media_last_run` (from `admin.backup_media`, classified fields only). A `*backup.SizeError` is a 413 naming size and member.
- Backup routes and theme writes are admin-only: capsules and settings carry site data and secrets. Export, pair-remote, deposit, unpair, pin-key and schedule use `requireFreshAdmin`: step-up is a sign-in from the last 10 minutes (`stepUpWindow`), which repeats password plus TOTP or the suite login for local and SSO admins alike; older sessions get 403 `reauthentication_required` with one generic message ("Confirm it's you: ..."), shared by every step-up route. `Session.CreatedAt` is the credential time: a session minted by `pair/verify` inherits the initiating session's time via `IssueDerivedSession`, so pairing cannot refresh an old session. SSO sessions carry the ID token's signed `auth_time` (zero when missing, which never passes); a KyIdentity admin's refusal includes `reauth_url` `/api/sso/kyidentity/login?fresh=1`, which forces `prompt=login` and `max_age=0`. Drill and status stay `requireAdmin`. The pin is write-once, so a stolen session pinning its own key first would own every later capsule. Routes are registered with method patterns, and because the `/api/` catch-all answers any method, tests pin that a wrong method never reaches a backup handler rather than expecting 405.

| POST | `/api/backup/pair-remote` | `handlePairRemoteRecovery` | `{recovery_key_id, threshold, total_shares}` |
| POST | `/api/backup/deposit` | `handleRunBackup` | `recoveryclient.Result` (+`receipt_unrecorded`) |

| POST | `/api/backup/pin-key` | `handlePinKey` | write-once; 409 on a different key |
| PUT | `/api/backup/schedule` | `handleSetSchedule` | `{interval_sec}` read back from the store |

- `POST /api/backup/deposit` is one `recoveryclient.Run`: seal once, deliver to the local directory and to KyRecovery when paired. 412 no key, key pin missing, no destination, no database snapshot, or a private destination with `KY_BACKUP_ALLOW_PRIVATE_RECOVERY` off; 409 key mismatch or a run in flight; 413 over the capsule caps; 502 when KyRecovery refused (`recoveryclient.ErrRemote`, naming a local copy that was written, so the `ErrPrivateDestination` arm must stay above it: the lib wraps both on the dial path); 500 for a failure before a byte left; 200 with `receipt_unrecorded` when the store holds the capsule but the receipt was not written. It runs on a context detached from the request with a 20-minute write deadline; the acting admin is resolved before the upload and the audit row is written on that same detached context.
- The write-once or irreversible backup handlers (`handlePairRemoteRecovery`, `handlePinKey`, `runBackup` behind both deposit routes, `handleUnpair`) run on `context.WithoutCancel(r.Context())` so a dropped connection cannot leave a pin, a pairing, a deposit or an unpair half-written with no audit row; `handleSetSchedule` stays on the request context. Every failure branch after input parsing is audited. Their routes are registered as `s.tracked(s.requireFreshAdmin(s.handleX))`, so the `detached` counter is incremented the moment `ServeHTTP` dispatches -- before `requireAdmin`'s session lookup, which is itself a store round-trip that `ReadTimeout` (15s) lets outlast `shutdownTimeout` (5s). Registering inside the handler was too late: `Shutdown` returns after its timeout with requests still active, and one still in the auth lookup would leave `WaitDetached()` reading zero and the store closing under a request about to pin a key. The header-read window before `ServeHTTP` is entered cannot be covered by any counter, because no handler goroutine exists yet; `Shutdown`'s own drain is what covers it. The counter is a mutex and a `sync.Cond`, not a `sync.WaitGroup`, which panics when an `Add` from zero races an in-progress `Wait` -- two admin requests at SIGTERM do exactly that. `WaitDetached()` is what `cmd/server` blocks on before closing the store, because `http.Server.Shutdown` returns without knowing these goroutines exist.
- Audit actions: `backup.paired`, `backup.pair_failed`, `admin.backup_run` (details start with `outcome="success|failure"`), `admin.backup_unpair`, `admin.backup_key_pin`, `admin.backup_schedule`, `admin.backup_export` (a downloaded capsule, resource the capsule ID). `AuditDetails` flattens the lib's details map into the bounded audit field with locally derived fields first and remote error text last; values are quoted and `=` is escaped before the final `AuditSafe` cut. `cmd/server` uses it for the scheduler and CLI rows. Details carry key or capsule IDs, digests and paths, never the token.
- Rate-limit keys for `login:`, `mfa:`, `pair:` and `password-change:` come from `auth.ClientIP` via `allowClientAttempt`, never from `RemoteAddr` or a raw header, so a limit is neither shared by everyone behind a proxy nor bypassable by forging `X-Forwarded-For`. IPv6 clients are keyed per /64. That map is capped and randomly evicts.
- Per-account windows (`login-user:`, `mfa-user:`, `password-change-user:`, `pair-init:`) use `allowAccountAttempt` with existing user IDs only, in a separate uncapped map that anonymous traffic cannot evict. Password login allows 10 attempts per account per 15 minutes, resolves only local accounts and runs a dummy hash for unknown names.
- Login, MFA and `pair/verify` mint sessions without a CSRF token, so `ServeHTTP` requires `Content-Type: application/json` on them (415 otherwise): a cross-site form cannot send it without a preflight that foreign origins fail. PoW solutions are single-use.
- `pair/verify` accepts only the QR `secret`, bounds device fields, returns one error for every miss and audits `device.paired`.
- CORS permits only the exact configured `KY_APP_URL` origin and credentialed browser writes require matching CSRF cookie/header tokens.
- API request bodies are capped at 1 MiB and all responses receive baseline CSP, anti-framing, MIME-sniffing, and referrer-policy headers. HSTS (`includeSubDomains`, with secure cookies) is sent only when `r.Host` matches the `KY_APP_URL` host (`hostMatches`): the Matrix server name is often the apex, and a year of HSTS there breaks plain-http services under it (`TestHSTSOnlyOnTheAppHost`).
- `Server.OnDirectoryChange(fn)` registers a callback run after each acknowledged KyIdentity directory webhook (never after a refused one); it must not block, as the sender is waiting. `cmd/server` passes the Matrix offboarding syncer's `Wake`.
- `GET /.well-known/matrix/client` (unauthenticated, registered before the SPA catch-all) returns `{"m.homeserver":{"base_url":<KY_MATRIX_HOST>}}` with `Access-Control-Allow-Origin: *`, no credentials header and no HSTS; JSON 404 when Matrix is not configured. `ServeHTTP` answers its `OPTIONS` preflight from any origin, the app's own included (200, `*`, no credentials), before the app-origin preflight rule (`wellknown_test.go`).
- `GET /api/settings` always carries `chat_url` (the Element origin, empty when Matrix is not configured) in the public tier; the members' "Open chat" link reads it.
- `GET /api/settings` tiers its payload: public fields for the login screen, `db_driver`/`scim_enabled` for any session, and `extra_settings` for admins only; KyRecovery tokens are omitted in both sealed and legacy plaintext forms, dropped by the `kyrecovery_token` key prefix rather than by literal key name.
- Matrix console routes (`matrix_handlers.go`, `health_handlers.go`, `audit_handlers.go`), all admin-only and `no-store`: `GET /api/admin/matrix/users?search&offset&limit` (MAS users joined to the KyIdentity directory; status `active|locked|deactivated|not_linked`), `GET /api/admin/matrix/users/{id}/sessions`, `POST /api/admin/matrix/sessions/{kind}/{id}/finish` (`requireFreshAdmin`, `tracked`, detached context; an ended session is `already_ended`), `GET /api/admin/health` (parallel probes; without Matrix only `kymessages` and `database`; with Matrix also `synapse`, `mas`, `element`, `postgres` and `synapse-admin`, which proves Synapse admin access through `MatrixAdmin.AsConsole` and `RoomAdmin`, a `synapseadmin.Client` on the probes' Synapse origin) and `GET /api/admin/audit?kind&offset&limit` (newest first; `kind` is `auth|backup|matrix|scim`; a present but empty or unknown value is 400; details are returned to admins, accepted). `limit` is 1-100, `offset` non-negative. Matrix routes answer 404 `matrix_disabled` until `SetMatrixAdmin` is called; `cmd/server` passes the same `matrixsync.Client` the sweep uses, so both share one token. Path IDs must be ULIDs. Audit kinds map to action prefixes: `auth` = `auth.`, `device.`; `backup` = `backup.`, `admin.backup_`, `restore.`; `matrix` = `matrix.`; `scim` = `scim.`. Rows with no user show actor `system`; `scim.*` rows show `scim` (their user ID is the provisioned user). Actor and target are clipped to 200 bytes of valid UTF-8 (`clip200`), because usernames and resources are unbounded and the web refuses a page with an oversized field. Finish audits `matrix.session_end` with resource the MXID (empty when MAS could not name the user) and details `outcome=... session=... kind=...` (`outcome` is `ended`, `already_ended`, `error: ...` or `refused: no user`); the outcome is shortened by whole runes until details fit AuditSafe's 200 bytes. Session IP and user agent are shown to admins and never logged or audited. Room routes (`room_handlers.go`), all through `MatrixAdmin.AsConsole` and `RoomAdmin`, admin-only and `no-store`: `GET /api/admin/matrix/rooms?search&offset&limit` (`{rooms, total, offset, limit}`; `search` at most 255 bytes; `closed` is Synapse's block flag, read per listed room), `GET /api/admin/matrix/rooms/{id}` (`{room, members, members_total, confirm_text, jobs}`; at most 1000 members shown, never messages) and `GET /api/admin/matrix/rooms/{id}/delete-status` (`{jobs:[{delete_id, status}]}`; the room need not exist). `POST .../rooms/{id}/close` and `POST .../rooms/{id}/delete` (`{"confirm":...}`) are `requireFreshAdmin`, `tracked` and run on a detached context; both answer `{outcome: started|already_closed, delete_id}` and are polled via delete-status. Close is final (block, members leave, history kept; no reopen); closing a closed, empty room is `already_closed`. The steps before the final Close or Delete get `roomChangeTimeout` (2m); that call gets its own `roomStartTimeout` (30s), and if it fails other than by Synapse's refusal the jobs are read again and a job not listed before is answered and audited as `started` with its `delete_id` (a lost reply must not hide an irreversible purge); with none listed, a failure that is not Synapse's own answer is audited as `error: no reply, the job may have started: ...`. The sum stays inside the 5-minute console session. The reply's write deadline is `roomWriteTimeout`: the budget plus `roomAfterBudget` (detached mint and revoke, final call, jobs recheck, audit write) plus 5s to write. Delete's body is exactly one JSON object with only `confirm` (unknown fields and trailing data are 400). Delete rechecks `confirm` against `confirm_text` (the name as shown, clipped to 200 bytes, or the room ID when the name is empty, starts or ends with whitespace, or holds control or format characters), then starts the purge. Delete removes no media: Synapse attributes to a room any local media its plaintext events name (forwarded images, an upgraded room's avatar, a reference planted by a member), which other rooms may still use, so the room's attachments and avatars stay in the media store. A change is refused with 409 while a listed job is scheduled or active, and on Synapse's own 400 "already in progress". Room IDs are checked against `roomIDPattern` (`!opaque[:server[:port]]`, at most 255 bytes, never `/`) before any Synapse call; otherwise 400. Errors: 404 `No such room`, 502 `Synapse admin access is not working: <cause>`. They audit `matrix.room_close` and `matrix.room_delete` with resource the room ID and details `outcome="..." [delete_id="..."]` via `auditFields` (outcome first, all quoted, shortened to 200 bytes); outcomes `started`, `already_closed`, `refused: confirmation does not match`, `refused: a close or delete is running`, `error: ...`. A malformed body or invalid ID is not audited. Room names and member lists are never logged or audited. The audit view's outcome comes from `detailOutcome`, which trusts an outcome only when the whole details string is `key="quoted"` tokens separated by single spaces; older unquoted rows show none.
