# Chat platform options: custom MLS, Matrix, XMPP and bridges

Checked 2026-10-01 against upstream repositories and release pages, the Matrix, XMPP and
IETF specifications, the target networks' first-party API documentation and terms, and this
repository. This is decision input, not an implementation plan. Nothing here was run
against a live deployment. Versions and dates are as of the check date.

Naming: the suite identity provider is **KyIdentity**. Code still uses legacy identifiers
for it: the `sso_provider` value `kysignon` and the `/api/sso/kysignon/...` routes
(`internal/api/server.go`, `internal/store/models.go`).

## 1. Decision summary

- **Established:** No bridge to any of the 15 target networks keeps end-to-end encryption. Each bridge is a client of the remote network and holds that network's plaintext on the bridge host. The only E2EE-preserving third-party route found is Meta's DMA interoperability for WhatsApp/Messenger. It is EU-only, needs a signed agreement with Meta, and covers 1:1 chats first. [Source](https://docs.mau.fi/bridges/general/end-to-bridge-encryption.html), [Source](https://developers.facebook.com/m/messaging-interoperability/), [Source](https://engineering.fb.com/2024/03/06/security/whatsapp-messenger-messaging-interoperability-eu/)
- **Established:** Maintained bridges exist almost only for Matrix (mautrix, releases 2026-09) and XMPP (Slidge, releases 2026-09). Custom MLS has no bridge ecosystem. [Source](https://github.com/mautrix/whatsapp/releases/tag/v0.2609.0), [Source](https://codeberg.org/slidge/slidge)
- **Established:** No maintained bridge was found for Teams, Zoom Team Chat, Zoho Cliq or Webex on any protocol. The only Teams bridge found was matterbridge, last released 2023-01-29.
- **Established:** Element (the largest commercial Matrix vendor) sold a managed Microsoft Teams bridge, but its docs now state: "The Teams bridge is no longer available for purchase. This documentation is for existing customers of the bridge only." Even while sold it needed a Teams admin and an Azure AD bot user, and "Connecting to a Teams workspace that you do not control is currently not supported" — it bridged your own tenant, not partners'. Checked 2026-10-01. [Source](https://docs.element.io/latest/element-cloud-documentation/integrations/teams-bridge/), [Source](https://ems-docs.element.io/books/element-cloud-documentation/page/teams-bridge), [Source](https://element.io/blog/ems-launches-bridging-for-microsoft-teams/)
- **Inference:** Teams is the business-critical target (owner, 2026-10-01). No protocol choice supplies a Teams bridge; a self-built Teams bot is the only route, and bridging to partner tenants likely needs each partner's admin consent (unverified against Microsoft's docs).
- **Established:** MLS in Matrix is still a proof of concept (MSC2883 open, WIP), and MIMI has no RFC yet. Neither lets you keep MLS and federate today. [Source](https://arewemlsyet.com/), [Source](https://datatracker.ietf.org/wg/mimi/documents/)
- **Inference:** If bridges are a requirement, the evidence favours a Ky-integrated Matrix deployment. The cost is real: PostgreSQL plus 3+ services, AGPL server components, Megolm instead of MLS, and discarding `chat-core`.
- **Inference:** If internal E2EE chat is the product and bridges are optional, keep custom MLS and treat any bridge as a separate, labelled, decrypting gateway. Either way, a bridged conversation can never carry the E2EE label.

## 3. Target-network matrix

Abbreviations:
- **E2EE survives?** is always "no" for bridges. **Decrypts at** names where the plaintext exists.
- mautrix bridges are linked or puppeted clients of the remote network. With end-to-bridge encryption on, the bridge re-encrypts into the Matrix room, so the homeserver does not see plaintext. The bridge host still does. [Source](https://docs.mau.fi/bridges/general/end-to-bridge-encryption.html)
- Slidge gateways are XMPP components and decrypt the same way: remote plaintext is on the gateway host (inference from the architecture; Slidge's E2EE handling was not checked).

## 5. Options for KyMessages

### (a) Keep custom MLS, no bridges in the core
- **Cost:** finish the release gates (client integration, deployed identity, browser evidence), and keep sole ownership of the protocol profile, delivery and device lifecycle. No mobile client exists.
- **Risk:** ts-mls is unaudited, and the only independent-implementation check (OpenMLS) failed the extensibility gate. (interop research removed; see git history) Users cannot pick an existing client.
- **Bridges:** none, unless built. mautrix-go's bridgev2 defines a `MatrixConnector` interface (mautrix-go v0.31.0, MPL-2.0). [Source](https://github.com/mautrix/go/blob/v0.31.0/bridgev2/matrixinterface.go) **Inference:** in principle that lets a non-Matrix host drive mautrix network connectors, but no third-party host was found, and the connectors are AGPL-3.0.
- **Thrown away:** nothing.

### (b) Ky-integrated Matrix deployment
- **Shape:** Synapse plus MAS, with KyIdentity as the only upstream provider and local passwords off. Registration and federation are disabled by default. Element Web and Element X are the clients. KyMessages becomes the control plane: console, KyRecovery capsules, health, and bridge enablement.
- **Bridges:** mautrix bridges are off by default and enabled per network by an admin, with end-to-bridge encryption on. Every bridged room is labelled "decrypted on this server by the <network> bridge". WhatsApp, Messenger and Discord user-mode bridges carry the ToS warnings above.
- **Lighter variant:** Tuwunel replaces Synapse and MAS. Unverified: KyIdentity compatibility, Element X behaviour, and its backup method.
- **Cost:** PostgreSQL, 3+ services and per-bridge databases. AGPL-3.0 for Synapse, MAS, Element and mautrix (see open questions).
- **Risk:** Megolm's 2022 homeserver-trust findings. The only vodozemac audit (2022) does not cover 0.11.1, so the "not independently audited" label still applies to the deployed version.
- **Thrown away:** `chat-core`, `mls-proof`, the delivery API and the device-approval flows. That is most of the encrypted-chat milestone work.

### (c) Hybrid: custom MLS for internal chat, separate bridge gateway
- **Shape:** keep (a) for E2EE rooms. Run an optional, admin-enabled gateway (a Matrix homeserver plus mautrix, or Slidge on XMPP) for external networks. Show bridged conversations as a distinct, non-E2EE room class in Ky clients.
- **Cost:** two stacks, plus a KyMessages-to-gateway link that is itself a decrypting endpoint. That link needs its own bot or device identity, visible in every room it joins.
- **Risk:** users mixing the two room classes. **Inference:** this is the most work, and is justified only if both E2EE-native rooms and bridges are must-haves.
- **Thrown away:** nothing, but the bridge half is new.

### Recommendation (Inference)
- If bridging to the listed personal networks is a hard requirement, take **(b)**. It gets maintained bridges, first-party mobile and web clients and upstream OIDC, and it keeps Ky's console, backup and identity integration. Accept Megolm in place of MLS and park `chat-core` until MSC2883 or MIMI is deployable.
- If bridges are a nice-to-have, finish **(a)**. Revisit (c) only with a named user need.
- Either way, team-suite connectors (Teams, Zoom, Zoho, Webex) are custom official-API work. Element's withdrawn Teams bridge (above) shows this is hard even for a funded Matrix vendor.
- Under every option, no bridged conversation may carry the E2EE label.

## 7. Spike: Matrix with KyIdentity sign-in (2026-10-01)

A throwaway loopback build tested option (b). It used Synapse v1.162.0, MAS 1.26.0, Element Web v1.12.30 and Postgres 17.6, with KyIdentity built from source at `c21445b`. The evidence was local only and was not kept, so the results are summarised here.

| Question | Result |
|---|---|
| KyIdentity as MAS's only upstream sign-in, local passwords off | Works. Only users assigned to the app in KyIdentity get in; unassigned users get `access_denied`. |
| Element Web signs in and sends a message | Works |
| Registration and federation closed | Works. Synapse `/register` returns 403, password login 400, federation endpoints 404, outbound "Federation denied". |
| Deactivating a user | Split. KyIdentity disable blocks new sign-ins only, and existing Matrix sessions keep working. Synapse admin deactivate is undone, because MAS issues fresh working sessions on the next sign-in. Only MAS admin-API deactivate locks the account. |
| Claims | KyIdentity's ID token carries everything MAS needs (`preferred_username`, `email`, `name`, `sub`) when the client requests `profile email`. MAS ignores `acr`. |

Backup scope: the Synapse and MAS databases, plus MAS `secrets.encryption`, restored from one point in time. Also the Synapse signing key, the `homeserver.yaml` secrets and `media_store/`. KyIdentity must keep each user's `sub` and the MAS client secret.

Open issues, all blocking a product:
- Resolved: KyIdentity disable ends live Matrix sessions. Back-channel logout into MAS (`logout_all`) cut an open Element session in 0.3-3.0 s (bound 30 s), with KyMessages running or stopped; KyMessages then locks the MAS user through the admin API. Evidence: `scripts/matrix-acceptance.sh` offboarding steps. A disable missed while KyMessages is down is held by KyIdentity until an operator resumes it.
- MFA enforcement through KyIdentity's per-app policy is untested.
- No Teams bridge exists for this stack either (see section 3).
- A public https deployment through cloudflared is untested. The acceptance harness runs the shipped configs over https with a private CA on loopback, which needs neither of the spike's MAS relaxations (`discovery_mode: insecure`, `allow_insecure_uris`).

Resolved by the stack work (`scripts/matrix-acceptance.sh`, same pinned versions):
- Username mapping (owner decision 2026-10-02: from the email). `matrix-init` maps the email's local part to a lowercase localpart, with every character outside `[a-z0-9._=-]` replaced by `_`. KyIdentity user `AQuinn` with email `Alice.Q+Ky@kymatrix.test` signs in as `@alice.q_ky`. An ID token without `email` (client scopes narrowed to `openid profile`) is refused by MAS with no account created, though MAS shows a raw "Unexpected error" page.
- The plaintext message. Reproduction, run on every PR with the compatibility login routed in the harness's scratch copy only:
  - Element signed in through MAS's compatibility layer (`m.login.sso`, then `m.login.token`; MAS records a compat session and no OAuth session) sets up encryption like a native session: device keys and all three cross-signing keys are uploaded. Its message in a new room is stored as `m.room.encrypted`. The anomaly does not reproduce through Element.
  - Synapse stores what a client sends. With the same compat session's token, a plain client-server API send of `m.room.message` into that encrypted room is stored as plaintext. So is the same send with a native OIDC session's token into a room Synapse encrypted by default. `m.room.encryption` instructs clients; the server does not enforce it.
  - Explanation: a plaintext event in an encrypted room needs a sender that does not encrypt. The compat sign-in alone does not produce one, and the room's encryption state was correct in every case. The spike's evidence was not kept, so the exact path of its one message is not known, but the only path the harness found is a non-encrypting sender, and it is open to any session, compat or native.
  - Consequence: encrypted storage is a property of the client. The shipped stack does not route the compatibility login, and the harness proves that Element, signed in through native OIDC, stores DM and group messages only as `m.room.encrypted`, with no plaintext anywhere in a dump of the Synapse database. A member using a non-encrypting client or script can still post plaintext into an encrypted room.
- The label: "End-to-end encrypted in Element (not independently audited)", exactly. The server does not enforce encryption, so a client that does not encrypt can post plaintext into an encrypted room, and nothing server-side stops it.
